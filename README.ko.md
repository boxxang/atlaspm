# AtlasPM

반도체 프로그램 관리 도구 — SoC 프로그램을 TPM 시점에서 보는 화면입니다. 로드맵,
스테이지별 보드, 산출물, 리스크, 그리고 프로그램 대시보드로 이루어져 있습니다.

> **English:** [README.md](README.md) · **로컬 설치:** [local/README.ko.md](local/README.ko.md)

`design-canvas/atlaspm-prototype.html` 이 단일 파일 프로토타입이자 **이 포팅의 스펙**입니다.
`reference/index.html` 은 최초 포팅의 스펙이었고 지금은 히스토리입니다 — 둘이 어긋나면
프로토타입이 이깁니다. 자세한 규칙은 `CLAUDE.md`, 진행 계획은 `PORTING_PLAN_V2.md` 를 보세요.

## 시작하기

배포본과 같은 엔진인 Postgres 를 씁니다.

```bash
brew install postgresql@17 && brew services start postgresql@17
createdb atlaspm_dev && createdb atlaspm_test
cp .env.example .env          # DATABASE_URL 을 atlaspm_dev 로

npm install
npm run db:push     # prisma/schema.prisma 로 스키마 생성
npm run db:seed     # AtlasAX1 프로그램 적재
npm run dev         # http://localhost:3000
```

`.env` 의 접속 문자열에는 **사용자 이름이 들어가야 합니다**
(`postgresql://내계정@localhost:5432/atlaspm_dev`). Homebrew 로 설치한 Postgres 에는
`postgres` role 이 없고 OS 사용자 이름의 role 만 있어서, 빠뜨리면 Prisma 가 P1010
"denied access" 를 냅니다.

`npm run db:reset` 은 push 와 seed 를 함께 돌려 AtlasAX1 을 원래 상태로 되돌립니다.

시드의 kickoff 은 시드를 돌린 날로부터 **66주 전**이라, "오늘"이 언제나 프로그램 중간
(Physical Design 부근)에 떨어집니다. 프로토타입이 부팅되는 모습 그대로입니다. 산출물은
스테이지 마지막 날에 몰리지 않고 기간에 걸쳐 흩어져 있고, 완료된 것은 마감일 며칠
전후로 찍혀 있어서, 시드된 프로그램이 실제로 굴러간 프로그램처럼 읽힙니다.

## 프로그램

툴바에는 프로그램, 그 프로그램이 올라탄 마일스톤 템플릿, 그리고 그 템플릿을 편집하는
입구가 있습니다. 날짜는 툴바에 없습니다 — 아래 마일스톤 축이 날짜를 시간 위에 놓고
보여주고, 읽고 고치는 곳도 거기입니다.

`/` 는 모든 프로그램을 카드로 보여줍니다. 진행률, kickoff, Tapeout 과 D-day, 열린 리스크,
지연 건수, 오늘 진행 중인 스테이지가 들어갑니다. 카드를 열면 `/p/[projectId]` 로 갑니다.

프로그램을 만들 때는 이름, 예상 kickoff, 일정 프로파일을 묻습니다. 제시되는 프로파일은
DB 에 있는 것들입니다 — 내장 `Typical SoC`, 그리고 누군가 프로그램의 스테이지를 편집하다
포크한 프로파일들. `Typical SoC (Customized)` 를 고르면 23개 스테이지 중 필요한 것만
골라 시작할 수 있고, kickoff 과 정렬할 기준 스테이지도 지정할 수 있습니다.

새 프로그램은 **빈 보드**로 시작합니다 — 핵심 정보도, 액티비티도, 리스크도, 리더도,
연락처도 없습니다. 그런 것들은 남의 예시 데이터니까요. 대신 스테이지 뼈대는 받습니다:
`/src/data/journey.ts` 의 스테이지별 표준 산출물이 각 스테이지 종료일로 날짜가 잡힌 채
들어갑니다. 마일스톤은 행이 아예 필요 없습니다 — 이 앱의 다른 모든 날짜처럼
kickoff + 프로파일 오프셋에서 파생됩니다.

프로그램마다 DB 가 들고 있는 것은 kickoff, 프로파일, 일정 override, 항목, 산출물, 리더,
연락처입니다. 스테이지 자체는 프로파일의 것이고, 같은 프로파일을 쓰는 모든 프로그램이
공유합니다.

## 구조

```
src/data/       내장 프로파일, journey 콘텐츠, 프로젝트 시드 — 순수, DOM 없음
src/lib/        일정 계산, 프로파일→스테이지 해석, 파생값, DB 접근
src/store/      Zustand 스토어 (앱 상태, 모달 상태)
src/components/ UI — 프로토타입에서 1:1 이식
src/app/        라우트(/ 프로그램 목록, /p/[projectId] 프로그램), 서버 액션
prisma/         스키마, 시드
local/          이 앱을 자기 PC 에 설치해 쓰기 위한 도구
```

순수 로직은 UI 를 import 하지 않고, `/src/lib` 과 `/src/data` 는 DOM 을 건드리지 않습니다.
`tests/unit/purity.test.ts` 가 둘 다 강제합니다.

## 프로토타입을 넘어 동작하는 것들

- **이메일 내보내기.** 봉투 버튼이 초안을 만들어 OS 메일 클라이언트에 넘깁니다. 대시보드는
  프로그램 요약을, 각 액티비티·리스크·핵심정보 행은 담당자 앞으로 자기 자신을 내보냅니다.
  담당자 주소는 프로그램의 리더·연락처에서 최선을 다해 찾습니다 — `Item.owner` 가 자유
  텍스트라 `src/lib/people.ts` 가 전체 이름, 약칭, 성 순으로 시도합니다. `mailto:` URL 은
  2KB 근처에서 잘리므로 본문은 꼬리를 잃는 대신 안내와 함께 줄입니다.
- **일정 미리보기.** 스테이지 날짜를 고치면 — 양쪽 끝 중 하나든, 사이의 주 수든 — 저장하지
  않고 **제안 상태로 올려둡니다**. 로드맵과 두 간트가 제안을 그리고 저장된 일정을 아래에
  흐리게 깔아둡니다. 함께 움직이는 스테이지와 마일스톤이 며칠씩 밀리는지 막대로 나열됩니다.
  Apply 가 커밋, Discard 가 되돌리기, 새로고침은 버립니다.
- **스테이지를 편집할 수 있습니다.** 툴바의 *Stages* 가 프로파일의 스테이지 목록을 엽니다 —
  이름 변경, 순서 변경, 다른 생명주기 밴드로 이동, 시작·기간 변경, 추가, 삭제.
- **스테이지 편집은 그 프로그램만의 일입니다.** 저장하면 지금 보고 있는 프로그램에만
  적용됩니다. 프로파일을 공유하던 프로그램이면 **조용히 사본으로 옮겨탄 뒤** 적용되므로,
  다른 누구의 일정도 바뀌지 않습니다. *Save as template…* 은 다른 이야기입니다 — 같은
  목록을 이름을 붙여 공개해서, 다른 프로그램이 그걸로 시작할 수 있게 합니다.
- **스테이지 상세 편집.** 세 가지가 따로 편집됩니다. 서로 다른 것들이기 때문입니다:
  Stage Details 헤더의 연필은 그 프로그램의 스테이지 *텍스트* 사본을 열고, 엔지니어링
  목록과 산출물은 각자 Edit 스위치를 갖습니다.
- **날짜 없는 산출물.** 마감일을 비운 채 추가하면 먼저 확인하고, 그게 의도였다면 **TBD**
  로 저장합니다. 체크하면 끝난 날이 찍히고, 편집 모드에서 그 날짜도 여느 날짜처럼 고칠 수
  있습니다. 실제로 끝난 뒤 며칠 지나 체크하는 일이 흔하니까요.
- **하나의 날짜 축, 두 번 읽기.** 로드맵은 상단에 생명주기 밴드와 마일스톤 다이아몬드를
  날짜 위치대로 싣고, 스테이지들은 동시성 차트의 y축이 됩니다. 둘이 같은 기하와 여백을
  쓰므로 다이아몬드가 자기가 표시하는 막대 끝 위에 정확히 앉습니다.
- **다이아몬드 위의 날짜.** 축의 모든 표시가 호버를 기다리지 않고 다이아몬드 안에 자기
  날짜(`10/15`)를 답니다. 모양과 굵기는 모두 같고 채움만 다른데, 그게 시간을 말합니다 —
  지나간 날짜는 채워지고 아직인 날짜는 비어 있어서, 축 자체가 진행 막대처럼 읽힙니다.
- **담당자 선택.** 항목의 담당자는 타이핑이 아니라 그 스테이지의 리더와 엔지니어링
  연락처에서 고릅니다. 약칭(`M. Bianchi`)으로 저장되어 Owner 열이 일관되고, 봉투 버튼이
  주소를 찾을 수 있습니다.
- **공수와 비용.** 스테이지의 엔지니어링 액티비티는 보드입니다 — 추가·이름변경·삭제, 각
  줄이 man-month 를 답니다. 스테이지 합계는 간트 막대에 타고, 프로그램 합계가 카드의
  추정 비용을 만듭니다. 단가는 프로그램 설정이고 대시보드에서 고칩니다. 기본값은 0 이라
  없는 비용을 지어내지 않습니다.
- **액티비티 상세.** 작성된 액티비티는 `/p/<id>/activity/<ref>` 에 자기 페이지를 엽니다 —
  왜 존재하는지, 어떤 스텝으로 굴러가는지, 무엇이 필요하고 무엇을 내놓는지, 누가 붙는지,
  무엇을 지켜봐야 하는지, 그리고 앞뒤 액티비티.
- **스테이지 타임라인.** 스테이지를 두 개의 표가 아니라 하나의 일정으로 읽습니다.
  엔지니어링 목록이 막대가 되고, 각 산출물은 그것을 만들어내는 액티비티의 막대 위에
  다이아몬드로 앉습니다. 스테이지 타임라인이 답해야 하는 질문은 "산출물 마감이 언제냐"가
  아니라 **"그게 존재하려면 무엇이 끝나야 하느냐"** 이기 때문입니다.
- **액티비티는 무언가를 향한 일입니다.** 액티비티를 쓸 때 어떤 핵심 산출물을 위한
  것인지를 지정하고, 그러면 Activity 보드를 산출물 하나씩 읽을 수 있습니다. 리뷰가
  시작하는 질문이 그것이지 "모든 태스크를 보여줘"가 아니니까요.
- **인도 기록.** 핵심 산출물은 체크박스로 완료되지 않습니다. 체크는 "했다"는 말이고,
  **산출물 그 자체가 그 일**입니다. 개발 이력과 거기서 나온 파일이 제목 옆 클립에서
  등록되고, 체크는 산출물이 붙었는지를 따라갑니다. 아무것도 붙이지 않고 등록하면 열린
  채로 남고, 마지막 산출물을 지우면 다시 열립니다. 몇 달 뒤의 질문은 "체크했나"가 아니라
  "무엇이 인도되었고 가는 길에 무슨 일이 있었나"입니다.
- **첨부.** 파일과 이미지는 항목을 쓰는 중에도, 이미 있는 항목에도(Edit 뒤에서), 상태
  업데이트에도 붙습니다. 바이트는 DB 에 삽니다(`Attachment.data`, `bytea`) — 배포 대상의
  파일시스템이 읽기 전용이고 인스턴스가 요청보다 오래 살지 않기 때문입니다. 그래서 파일당
  5MB 제한이 있습니다. PNG·JPEG·GIF·WebP 만 인라인으로 렌더되고, SVG 를 포함한 나머지는
  `nosniff` 와 함께 다운로드로 제공됩니다. 같은 오리진에서 온 사용자 콘텐츠를 인라인으로
  띄우는 것은 XSS 통로이기 때문입니다.
- **팝업 하나, 화면 셋이 아니라.** *Show more* 는 목록을 위에 둔 채 보드를 창으로 엽니다.
  항목 열기·새로 쓰기·기존 것 고치기가 모두 그 아래 창에서 일어나고, 지금 보고 있는 행이
  목록에서 표시됩니다.

## 프로토타입이 다시 정의한 것들

프로토타입은 몇 가지를 **추가가 아니라 재정의**했습니다. 앱은 이 정의를 따릅니다:

- **스텝이 상태를 가집니다.** 액티비티의 스텝은 완료 여부, 퍼센트, 담당자, 마감일, 완료일,
  붙은 산출물, 포스트 스레드를 갖습니다.
- **리스크는 스텝에 붙은 플래그**입니다. 별도의 항목 종류가 아닙니다.
- **지연(overdue)은 마감일을 넘긴 스텝**입니다. 목표일을 넘긴 항목이 아닙니다.
- **산출물은 인도(handover)로 완료됩니다** — 본문과 최소 한 개의 첨부, 그리고 완료일을
  갖춘 포스트입니다. 체크박스가 아닙니다.
- 스텝·리스크·노트·인도는 모두 "첨부와 답글을 가진 포스트" 하나의 모양입니다. 넷이 아니라
  하나입니다.

## 파생되는 값 (저장하지 않습니다)

스테이지 날짜(kickoff + 오프셋), 마일스톤(스테이지 종료에 고정), 진행률(완료 산출물 ÷
전체), 지연(마감일이 지났는데 인도가 없는 스텝), 리스크 빨간 막대(live 리스크 플래그가
있는 스테이지), TODAY 마커.

## 영속성

개발·e2e·배포 모두 Prisma + Postgres 입니다.

한때 로컬은 SQLite, 프로덕션은 Postgres 였는데 그건 성립하지 않습니다. Prisma 는
`provider` 를 generate 시점에 고정하고 환경변수에서 읽지 않으므로 둘이 스키마를 공유할 수
없고, 배포되는 엔진과 다른 엔진에서 도는 테스트 스위트는 실제로 배포되는 것을 테스트하는
게 아닙니다. 엔진 하나로 통일하는 비용은 `brew install` 한 번이고, 그걸로 둘 다 해결됩니다.

Prisma 7 은 접속 URL 을 스키마 밖에 둡니다. Migrate 는 `prisma.config.ts` 에서 읽고,
`PrismaClient` 는 드라이버 어댑터를 받습니다.

읽기는 서버 컴포넌트를 지나고(`getProjectState()`), 클라이언트 스토어는 RSC 페이로드로
부팅합니다. 쓰기는 `src/app/actions.ts` 의 서버 액션입니다. UI 가 먼저 낙관적으로
갱신되고 액션이 뒤따릅니다. id 는 클라이언트에서 만들어져서 낙관적 행과 저장된 행이 같은
정체성을 공유합니다.

"오늘"은 서버가 아니라 클라이언트에서 적용됩니다. TODAY 마커와 지연 건수는 보는 사람의
타임존에 속하므로, 스토어는 마운트 시점에 하이드레이트합니다.

### 표시 설정은 DB 가 아니라 localStorage 에

(`atlaspm.display.v1`) 글자 크기, 아이콘 배율, 막대 두께, 대시보드 행 높이, 드래그한 열
너비는 브라우저별 취향입니다. 이 단계에는 인증이 없으므로 `DisplaySettings` 테이블은
DB 전역이 됩니다 — 한 사람이 폰트를 키우면 모두에게 커집니다. 대가는 설정이 브라우저와
기기를 따라오지 않는다는 것이고, 사이트 데이터를 지우면 초기화됩니다. 인증이 생기면
사용자 id 로 키를 잡은 행으로 옮기면 됩니다. 저장 모양이 이미 `{ scope, json }` 이라
재설계가 아니라 읽기/쓰기 교체입니다.

## 테스트

```bash
npm test          # 401개 유닛 테스트
npm run e2e       # 147개 Playwright 테스트
```

e2e 스위트는 자기 DB(`atlaspm_test`)에서 돌기 때문에 개발용 DB 나 돌고 있는 dev 서버를
건드리지 않습니다. `TEST_DATABASE_URL` 로 덮어쓸 수 있습니다. 매 테스트가 실행 전에
in-process 로 다시 시드하는데, 그래서 스위트가 단일 워커입니다 — 병렬 워커는 서로의
발밑에서 시드를 갈아치우게 됩니다.

**dev 서버가 떠 있으면 e2e 가 시작하지 못합니다.** 3000번을 먼저 내려주세요.

쓰기가 낙관적이고 fire-and-forget 이라, `tests/e2e/fixtures.ts` 가 진행 중인 POST 를 세어
네비게이션 전에 비웁니다. 그러지 않으면 새로고침이 검증하려던 바로 그 액션을 취소합니다.

### 프로토타입과 비교하기

프로토타입을 프로덕션 빌드(`npm run build && npm start`) 옆에 놓고 봅니다. dev 빌드는
Next 의 개발 도구 배지가 붙는데, 그것만이 유일한 차이입니다. 프로토타입은 `file://` 로
열리지 않으므로 디렉터리를 서브해야 합니다:

```bash
cd design-canvas && python3 -m http.server 8765
```

## 배포

**인증이 없습니다.** 배포된 것은 누구나 읽고 쓸 수 있습니다. 진짜 내용을 담기 전에 접근
제어 뒤에 두세요. 회사 자료를 다루신다면 배포본 대신 [local/README.ko.md](local/README.ko.md)
의 로컬 설치를 쓰는 편이 낫습니다.

배포는 Vercel 이 GitHub 저장소를 보고 `main` 을 빌드합니다. **`main` 에 푸시하는 것이 곧
릴리스입니다.** 브랜치에서 작업하고 `--ff-only` 로 머지한 뒤 푸시하세요.

`npm run build` 가 `prisma db push && next build` 라서, 배포가 자기 스키마를 함께
가져갑니다. 추가형 변경(nullable 컬럼, 기본값 있는 컬럼, 새 테이블)은 알아서 적용됩니다.
파괴적 변경은 배포를 멈추는데, 그건 고장이 아니라 안전장치입니다 — 실패한 빌드는 직전
성공 배포가 계속 서빙하므로 비용도 없습니다. 데이터를 먼저 손으로 옮기고 다시 배포하세요.

`prisma/migrations` 는 없습니다. 이 저장소는 선언적인 `db push` 방식이고, **`db push` 는
데이터를 옮기지 않습니다.**

자세한 절차와 함정은 `CLAUDE.md` 의 *Shipping it* 에 있습니다.
